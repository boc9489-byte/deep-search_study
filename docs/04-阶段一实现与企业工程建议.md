# 阶段一实现与企业工程建议

> 阶段一目标：在不依赖真实 LLM、搜索 API、向量库和数据库的前提下，跑通 DeepSearch 的最小可用闭环，并把后续生产替换点预留清楚。

---

## 1. 阶段一交付范围

阶段一不追求“搜索质量最强”，而是先保证系统主干是对的：

```text
创建项目
  -> 自动生成研究任务书和大纲
  -> 人工确认 / 修改大纲
  -> 提交研究报告任务
  -> 拆解原子问题
  -> 多源检索桩工具
  -> Evidence Pipeline
  -> Fact / Insight
  -> 确定性 HTML 报告
  -> Trace 与冒烟测试
```

本阶段已实现：

| 能力 | 实现文件 | 阶段一说明 |
| --- | --- | --- |
| FastAPI 服务入口 | `app/main.py` | 暴露健康检查、项目、任务、报告接口 |
| API Schema | `app/schemas/api.py` | 固定前后端接口契约 |
| Domain Model | `app/schemas/domain.py` | 固定 Evidence、Fact、Insight、Report 等内部契约 |
| 内存仓储 | `app/repository.py` | 无外部依赖跑通项目、任务、报告状态 |
| 后台任务 | `app/background.py` | 用 `asyncio.create_task` 承接长耗时任务 |
| Agent 抽象 | `app/agents.py` | 当前为确定性桩，生产替换为真实 LLM |
| Tool 抽象 | `app/tools/` | Web Search、RAG Search、Page Extract、Rerank 均可替换 |
| 工作流编排 | `app/workflow/` | 优先 LangGraph，未安装时降级本地线性执行器 |
| Evidence Pipeline | `app/pipeline/evidence_pipeline.py` | 标准化、去重、打分、排序、截断 |
| 报告渲染 | `app/report.py` | 从结构化数据确定性渲染 HTML |
| 冒烟测试 | `scripts/smoke.py` | 人工运行验证主链路 |
| 自动化测试 | `tests/test_stage1.py` | 覆盖 Pipeline 与端到端阶段一闭环 |

## 2. 阶段一技术选型

### 2.1 Web 框架

| 方案 | 优点 | 缺点 | 阶段一选择 |
| --- | --- | --- | --- |
| FastAPI | async 原生、Pydantic 契约、OpenAPI 自动生成 | 大型工程需要自行约束分层 | 选择 |
| Flask | 简单、生态成熟 | async 和类型契约弱，需要额外扩展 | 不选 |
| Django | 后台管理、ORM 完整 | 对 Agent 工作流偏重，启动成本高 | 不选 |

选择 FastAPI 的原因：本项目是 API + 长任务 + Pydantic Schema 驱动，FastAPI 更贴合。

### 2.2 工作流编排

| 方案 | 优点 | 缺点 | 阶段一选择 |
| --- | --- | --- | --- |
| LangGraph | 状态显式、节点可追踪、支持 checkpoint | 初期多一个依赖和学习成本 | 生产推荐 |
| 本地线性执行器 | 无依赖、便于 smoke test | 不适合复杂分支和断点恢复 | 阶段一兜底 |
| Celery Chain | 任务队列成熟 | 表达 Agent 状态图不如 LangGraph 自然 | 后台任务可用，不替代图 |

当前实现采用“双路径”：安装 LangGraph 时走 `StateGraph`，未安装时走 `LinearResearchRunner`，保证本地开箱即用。

### 2.3 后台任务

| 方案 | 优点 | 缺点 | 阶段一选择 |
| --- | --- | --- | --- |
| `asyncio.create_task` | 零依赖、适合 PoC | 进程重启丢任务，不支持分布式重试 | 选择 |
| Celery | 成熟、重试、定时、分布式 | 依赖 Redis/RabbitMQ，配置重 | 生产推荐 |
| RQ / Arq | 更轻量 | 能力弱于 Celery | 中小规模可选 |

阶段一用 `asyncio` 是为了降低运行门槛；生产环境必须替换为独立队列。

### 2.4 存储

| 方案 | 优点 | 缺点 | 阶段一选择 |
| --- | --- | --- | --- |
| 内存字典 | 无依赖、测试简单 | 不持久化，不支持多进程 | 选择 |
| PostgreSQL | 强一致、事务、查询能力强 | 需要迁移和连接管理 | 生产推荐 |
| MongoDB | 文档结构灵活 | 复杂关系和审计弱于 PG | 可作为补充 |

本项目核心对象有明确关系：Project、Task、Evidence、Fact、Report，因此生产优先 PostgreSQL。

### 2.5 检索与知识库

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| 向量检索 | 语义召回强 | 关键词、编号、表格字段命中不稳定 | 必备但不能单独使用 |
| BM25 / ES | 关键词强匹配、可解释 | 语义泛化弱 | 与向量检索互补 |
| Hybrid + RRF | 兼顾语义和关键词 | 需要融合调参 | 企业推荐 |
| Reranker | 提升 TopK 精度 | 增加延迟和成本 | 关键链路推荐 |

企业知识库建议采用：

```text
Query Rewrite
  -> Dense Retrieval + BM25
  -> RRF Fusion
  -> Rerank
  -> Evidence Pipeline
```

## 3. 配置设计说明

配置集中在 `app/config.py`，阶段一保留代码默认值，生产再迁移到 `.env`、环境变量或配置中心。

关键配置：

| 配置 | 作用 | 生产调参建议 |
| --- | --- | --- |
| `web_top_k` | 单次公网搜索候选数 | 受搜索 API 成本影响，先 5-10 |
| `kb_top_k` | 内部知识库候选数 | Hybrid 检索可拆成 dense/sparse top_k |
| `per_question_keep` | 每个原子问题保留证据数 | 控制上下文长度和报告引用密度 |
| `max_concurrent_questions` | 并发处理子问题数 | 结合 LLM、搜索、解析 API 限流 |
| `EvidenceScoreWeights` | 证据融合评分权重 | 根据业务偏好调整可信度/新鲜度/相关性 |
| `QualityThresholds` | 事实和洞察入报告门槛 | 生产应基于 Golden Set 调整 |
| `credibility_whitelist` | 来源可信度基础分 | 企业应维护权威来源白名单和黑名单 |

阶段一新增了更明确的配置注释，说明每个参数的生产含义和调参方向。

## 4. 测试方案

阶段一测试分三层。

### 4.1 单元级：Evidence Pipeline

目标：

- URL 和正文重复能够去重；
- 每条证据能够生成 quote；
- 综合分 `final` 大于 0；
- 输出按 `final` 降序。

测试文件：

```text
tests/test_stage1.py
```

### 4.2 端到端级：主链路

覆盖：

```text
project_repo.create
  -> run_generate_brief
  -> outline_ready
  -> outline_confirmed
  -> run_generate_report
  -> report_ready
  -> report / source / evidence / fact / insight / trace 非空
```

这个测试不启动 HTTP 服务，直接驱动 repository + background，速度快、依赖少。

### 4.3 冒烟测试

人工验证命令：

```bash
cd deepsearch
python -m scripts.smoke
```

自动化测试命令：

```bash
cd deepsearch
python -m unittest discover -s tests
```

## 5. 阶段一验收标准

| 验收项 | 标准 |
| --- | --- |
| 项目创建 | 返回 `project_id` 和 `initial_task_id` |
| 大纲生成 | 任务成功，项目状态变为 `outline_ready` |
| 大纲确认 | 项目状态变为 `outline_confirmed` |
| 报告任务 | 任务成功，项目状态变为 `report_ready` |
| 证据链 | `sources/evidences/facts/insights` 均非空 |
| 报告 | 生成 HTML，标题包含研究主题 |
| Trace | 至少包含计划、检索、洞察、报告渲染节点 |
| 测试 | `scripts.smoke` 和 `unittest` 均通过 |

## 6. 企业工程建议

### 6.1 分层边界

保持当前边界，不要把所有逻辑塞进一个 Agent：

```text
Router: 参数校验和响应
Repository: 状态和数据访问
Background: 长任务调度
Workflow: 状态机编排
Agent: LLM 决策
Tool: 外部能力
Pipeline: 证据质量控制
Report: 确定性渲染
Eval: 质量回归
```

### 6.2 生产替换顺序

建议顺序：

```text
真实 LLM
  -> 真实搜索 API
  -> 网页正文抽取
  -> 内部知识库 Hybrid Search
  -> Reranker
  -> PostgreSQL
  -> Celery / Arq
  -> LangGraph Checkpointer
  -> OpenTelemetry + Golden Set
```

这样可以每一步都观察质量变化，避免一次性接太多组件导致问题难定位。

### 6.3 可靠性

生产必须补：

- 任务幂等：同一个任务重复执行不会生成冲突版本；
- 失败重试：搜索、网页解析、LLM、rerank 分别设置重试；
- 超时控制：外部工具调用都要有 timeout；
- 降级策略：搜索失败时用内部库，rerank 失败时用基础分；
- 任务取消：用户可以取消长耗时研究；
- 版本管理：报告和大纲都应保留版本。

### 6.4 安全与权限

企业场景必须考虑：

- 用户、组织、项目三层数据隔离；
- 内部知识库按权限过滤；
- Trace 中避免记录敏感全文；
- 报告导出前做敏感词和权限检查；
- 外部搜索结果进入报告前标记来源类型；
- 对 LLM 输入输出做审计和脱敏。

### 6.5 可观测性

每个节点至少记录：

```text
trace_id
project_id
task_id
node_name
input_summary
output_summary
latency_ms
token_usage
evidence_count
source_count
model_name
prompt_version
error
```

后续可以接 OpenTelemetry、Prometheus、Grafana 或 LangSmith 类平台。

### 6.6 评估闭环

不要只看生成报告“像不像”。建议建立 Golden Set：

| 评估对象 | 指标 |
| --- | --- |
| 检索 | Recall@K、MRR、Context Recall |
| 重排 | Context Precision、TopK 命中率 |
| 引用 | 引用准确率、无效引用率 |
| 事实 | Faithfulness、冲突识别率 |
| 报告 | 结构完整性、结论一致性、可读性 |
| 系统 | 成功率、平均耗时、平均成本 |

每次改 Prompt、检索参数、rerank 模型、报告模板，都应跑一遍回归。

---

## 7. 阶段二建议

阶段二优先做三件事：

1. 接入真实 LLM，并要求结构化 JSON 输出；
2. 接入真实 Web Search 和网页正文抽取，替换 snippet 式证据；
3. 给 Evidence Pipeline 增加 Golden Set 评估，形成可量化调参闭环。

阶段二完成后，DeepSearch 才真正从“工程骨架”进入“真实资料驱动的企业研究 Agent”。
