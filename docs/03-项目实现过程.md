# DeepSearch 项目实现过程

> 本文记录 DeepSearch 企业级深度搜索研究平台从需求拆解到工程落地的实现过程。配套设计文档见 `01-概要设计与技术方案.md`、`02-接口与子系统设计.md`。

---

## 1. 项目目标确认

DeepSearch 不是普通搜索框，也不是一次性 RAG 问答，而是面向行业研究、竞品分析、战略判断等复杂任务的研究型 Agent 工作流。

核心目标拆成四点：

1. 用户输入研究主题后，系统自动生成研究任务书和初始大纲。
2. 用户确认或修改大纲后，系统围绕大纲叶子节点拆解原子问题并多源检索。
3. 检索结果统一进入 Evidence Pipeline，完成标准化、去重、打分、排序和交叉验证。
4. 最终生成带引用、可追溯、可复核的 HTML 研究报告。

本期工程定位为可运行骨架：LLM、搜索、内部知识库、存储等外部能力先用接口和桩实现，保证无需外部服务即可跑通主链路；生产环境再逐步替换为真实模型、搜索服务、向量库、数据库和任务队列。

## 2. 需求拆解与主链路设计

根据业务流程，把人工研究员的工作拆成如下主链路：

```text
创建项目
  -> 生成研究任务书
  -> 生成研究大纲
  -> 人工确认 / 修改大纲
  -> 提交报告任务
  -> 拆解原子检索问题
  -> 多源检索与网页/知识库读取
  -> 证据标准化、去重、排序
  -> 事实卡片与洞察卡片生成
  -> 确定性报告渲染
  -> 保存报告、证据和 trace
```

对应代码主链路：

```text
routers/projects.py
  -> repository.py
  -> background.py
  -> workflow/graph.py
  -> workflow/nodes.py
  -> agents.py + tools/
  -> pipeline/evidence_pipeline.py + pipeline/crosscheck.py
  -> report.py
```

设计原则：

- **LLM 只负责语义决策**：任务理解、大纲生成、问题拆解、事实和洞察合成。
- **工程链路尽量确定性**：证据去重、评分、引用绑定、报告结构渲染都用可复算逻辑实现。

## 3. 工程目录搭建

项目工程位于 `deepsearch/` 目录，按分层架构组织：

```text
deepsearch/
├── app/
│   ├── main.py                  # FastAPI 应用入口
│   ├── config.py                # 配置、阈值、权重
│   ├── routers/                 # HTTP 接口层
│   ├── schemas/                 # API 和领域模型
│   ├── repository.py            # 数据访问层，本期为内存仓储
│   ├── background.py            # 后台异步任务调度
│   ├── agents.py                # 研究管理智能体、检索智能体、LLM 抽象
│   ├── tools/                   # Web 搜索、RAG 搜索、网页解析、重排工具
│   ├── pipeline/                # Evidence Pipeline 与交叉验证
│   ├── workflow/                # LangGraph / 本地执行器
│   └── report.py                # 确定性 HTML 报告渲染
├── docs/                        # 设计与实现文档
├── scripts/smoke.py             # 端到端冒烟测试
├── requirements.txt
└── README.md
```

这样拆分后，接口层、任务编排、Agent 决策、工具能力、证据处理、存储和报告生成之间都有清晰边界，方便后续替换真实基础设施。

## 4. 数据模型与状态机实现

先在 `app/schemas/domain.py` 和 `app/schemas/api.py` 中定义系统契约。

核心领域对象包括：

| 对象 | 作用 |
| --- | --- |
| `ResearchBrief` | 结构化研究任务书，保存主题、目标、范围和默认假设 |
| `OutlineNode` | 研究大纲节点，支持多级树结构 |
| `AtomicQuestion` | 从大纲叶子节点拆出的原子检索问题 |
| `Evidence` | 统一证据对象，承接 Web、知识库、网页解析等结果 |
| `FactCard` | 基于证据交叉验证后的事实卡片 |
| `InsightCard` | 基于事实合成的洞察卡片 |
| `Source` | 来源对象，用于报告引用绑定 |
| `Report` | HTML 报告版本 |
| `TraceEvent` | 节点级执行 trace |

项目状态流：

```text
brief_generating
  -> outline_ready
  -> outline_revising -> outline_ready
  -> outline_confirmed
  -> researching
  -> report_ready
```

任务状态流：

```text
queued -> running -> succeeded | failed
```

状态机让前端可以清楚判断下一步应该等待、确认大纲、修改大纲，还是提交报告任务。

## 5. FastAPI 接口实现

接口层在 `app/main.py` 中注册路由，业务接口统一挂到 `/api/v1` 下。

主要接口：

| 接口 | 方法 | 实现要点 |
| --- | --- | --- |
| `/health` | GET | 服务健康检查 |
| `/api/v1/research-projects` | POST | 创建项目，并自动投递大纲生成任务 |
| `/api/v1/research-projects/{project_id}/outline` | GET | 查询当前研究大纲 |
| `/api/v1/research-projects/{project_id}/outline` | PUT | 确认或按自然语言修改大纲 |
| `/api/v1/research-projects/{project_id}/report-tasks` | POST | 创建研究报告任务 |
| `/api/v1/tasks/{task_id}` | GET | 查询后台任务状态 |
| `/api/v1/tasks/{task_id}/trace` | GET | 查询任务执行 trace |
| `/api/v1/research-projects/{project_id}/reports/latest` | GET | 获取最新报告 |
| `/api/v1/research-projects/{project_id}/evidence` | GET | 查询项目证据 |

接口层只做三件事：

1. 使用 Pydantic 校验请求参数。
2. 调用 repository 创建或读取项目、任务、报告。
3. 对耗时动作投递 background 任务，不在 HTTP 请求内同步执行长流程。

## 6. Repository 与后台任务实现

`app/repository.py` 隔离存储细节。本期用内存字典保存项目和任务，并用 `asyncio.Lock` 保证协程安全。

生产替换时，接口层和工作流不需要感知底层变化，只需要把 repository 实现替换为：

```text
Project / Task / Report / Trace -> PostgreSQL
Evidence / Fact / Insight       -> PostgreSQL 或文档库
向量数据                         -> Milvus / pgvector / Qdrant
报告 HTML / PDF / Docx           -> 对象存储
```

`app/background.py` 实现三类后台作业：

| 作业 | 触发时机 | 核心逻辑 |
| --- | --- | --- |
| `run_generate_brief` | 创建项目后 | 理解研究主题，生成任务书和大纲 |
| `run_revise_outline` | 用户修改大纲时 | 根据自然语言指令更新大纲 |
| `run_generate_report` | 用户提交报告任务后 | 驱动研究工作流，保存证据、事实、洞察和报告 |

本期用 `asyncio.create_task` 投递任务；生产环境建议替换为 Celery、RQ、Arq 或工作流平台，以支持独立 worker、失败重试、任务取消和横向扩容。

## 7. Agent 层实现

`app/agents.py` 把“哪里使用 LLM”集中管理，避免 LLM 调用散落在业务代码里。

### 7.1 ResearchManagerAgent

研究管理智能体负责编排型语义任务：

```text
understand_brief      # 研究主题 -> ResearchBrief
generate_outline      # ResearchBrief -> OutlineNode[]
revise_outline        # 旧大纲 + 修改意见 -> 新大纲
plan_questions        # 大纲叶子节点 -> AtomicQuestion[]
synthesize_facts      # Evidence[] -> FactCard[]
synthesize_insights   # FactCard[] -> InsightCard[]
```

当前方法返回确定性桩结果，目的是本地可运行。生产接入真实 LLM 时，建议使用结构化输出或工具调用，约束模型只返回 JSON，再转换为领域对象。

### 7.2 RetrievalAgent

信息检索智能体负责执行型检索任务：

```text
AtomicQuestion
  -> decide_route
  -> WebSearchTool / RagSearchTool
  -> EvidencePipeline
  -> ranked Evidence[]
```

当前默认同时查公网桩工具和内部知识库桩工具。生产环境可扩展为根据问题类型动态选择 Web Search、Vector Search、BM25、SQL、File Search 或业务工具。

## 8. Workflow 编排实现

`app/workflow/graph.py` 提供统一执行入口 `get_research_executor()`。

执行策略：

1. 如果环境安装了 `langgraph`，优先构建 `StateGraph`。
2. 如果未安装 `langgraph`，降级为 `LinearResearchRunner`，按相同节点顺序执行。

研究执行节点位于 `app/workflow/nodes.py`：

```text
plan_questions
  -> retrieve_and_build_facts
  -> build_insights
  -> assemble_report
```

节点职责：

| 节点 | 输入 | 输出 |
| --- | --- | --- |
| `plan_questions` | 已确认大纲 | 原子检索问题列表 |
| `retrieve_and_build_facts` | 原子问题列表 | Evidence、FactCard、Source |
| `build_insights` | FactCard | InsightCard |
| `assemble_report` | 大纲、事实、洞察、证据、来源 | HTML Report |

其中检索节点使用 `asyncio.Semaphore` 控制并发，避免实际接入搜索、网页解析、模型服务后并发失控。

## 9. Evidence Pipeline 实现

`app/pipeline/evidence_pipeline.py` 是项目核心工程资产。它把异构搜索结果统一处理为高质量证据。

完整流程：

```text
raw Evidence
  -> normalize
  -> dedup
  -> rank
  -> keep TopN
```

### 9.1 Normalize

调用 `PageExtractTool.enrich()` 补充正文，并从正文里抽取关键摘录 `quote`。生产环境可替换为 `httpx + trafilatura/readability` 或内部网页解析服务。

### 9.2 Dedup

使用 URL 归一化和内容指纹去重：

```text
URL 归一：netloc + path
内容指纹：正文 token 集合生成简化 fingerprint
```

生产环境可升级为 SimHash、MinHash 或语义聚类，处理近似重复内容。

### 9.3 Rank

使用多因子融合评分：

```text
final = relevance * w1
      + credibility * w2
      + freshness * w3
      + diversity * w4
      + rerank * w5
```

评分维度：

| 分数 | 含义 |
| --- | --- |
| `relevance` | 与原子问题的相关性 |
| `credibility` | 来源可信度 |
| `freshness` | 发布时间新鲜度 |
| `diversity` | 来源多样性，同域名重复降权 |
| `rerank` | 重排模型分数 |

最终每个原子问题保留 TopN 证据，减少后续 LLM 和报告渲染压力。

## 10. 交叉验证与报告生成实现

事实生成后会进入 `app/pipeline/crosscheck.py` 做交叉验证，核心目的是判断一个事实是否有足够证据支撑，并记录置信度和冲突信息。

报告生成在 `app/report.py` 中实现，采用确定性 HTML 模板渲染，而不是独立报告 Agent。

引用绑定链路：

```text
FactCard.supporting_evidence
  -> Evidence.source_id
  -> Source 顺序号
  -> HTML 角标 [n]
```

这种设计的好处：

1. 报告结构稳定，便于 diff 和回归测试。
2. 引用来源由程序绑定，不依赖 LLM 自己编引用。
3. 每个事实都可以回溯到 Evidence 和 Source。
4. 后续可以在同一结构数据上扩展 Markdown、PDF、Docx 或前端富文本报告。

## 11. 端到端验证

项目提供 `scripts/smoke.py` 做端到端冒烟测试，不启动 HTTP 服务，直接驱动 repository 和 background。

验证流程：

```text
创建项目
  -> 等待大纲生成
  -> 确认大纲
  -> 投递报告任务
  -> 等待报告生成
  -> 读取最新报告
  -> 打印来源数、证据数、事实数、洞察数、trace 事件数
```

运行方式：

```bash
cd deepsearch
python -m scripts.smoke
```

预期结果是主链路冒烟测试通过，并输出报告标题、报告版本、来源数量和 HTML 片段。

## 13. 生产化演进路线

| 阶段 | 改造点 | 目标 |
| --- | --- | --- |
| 第一阶段 | 接入真实 LLM、真实搜索 API、网页解析 | 让报告基于真实资料生成 |
| 第二阶段 | 接入内部知识库、向量库、BM25、RRF、Rerank | 提升企业私域资料召回质量 |
| 第三阶段 | 内存仓储替换为 PostgreSQL + 对象存储 | 支持多用户、多项目和报告版本持久化 |
| 第四阶段 | `asyncio.create_task` 替换为 Celery/RQ/Arq | 支持长任务重试、取消、扩容和任务隔离 |
| 第五阶段 | LangGraph checkpointer、节点级恢复、OpenTelemetry | 增强可观测性和失败恢复能力 |
| 第六阶段 | 构建 Golden Set、引用准确率、事实一致性评测 | 建立 RAG/Agent 质量闭环 |

## 14. 面试表达版实现总结

这个项目的实现可以这样概括：

> 我做的是一个企业级深度搜索研究平台，目标是把人工研究员“拆问题、查资料、筛证据、写报告”的过程工程化。实现上我用 FastAPI 提供项目、任务、大纲、报告等接口；用后台任务承接长耗时研究流程；用 LangGraph 或本地执行器编排 Plan、Search、Evidence、Verify、Report 节点；用 ResearchManagerAgent 负责大纲生成、问题拆解、事实和洞察合成；用 RetrievalAgent 统一调度公网搜索和内部知识库；核心质量控制放在 Evidence Pipeline 中，完成标准化、去重、可信度/新鲜度/多样性/重排打分；最终报告不让 LLM 自由生成，而是基于结构化事实和来源做确定性 HTML 渲染，保证引用可追溯、结果可复核。

项目亮点主要有三点：

1. 把复杂研究任务拆成显式工作流，避免普通 Agent 黑盒执行。
2. 把异构检索结果统一成 Evidence，并通过管道做质量控制。
3. 报告引用由程序确定性绑定，降低幻觉和伪引用风险。
